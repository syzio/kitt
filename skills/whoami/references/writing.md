# Writing rules

The text kitt skills write follows these rules. They are the short form of the unslop skill (`/kitt:unslop`), and the numbers in brackets match its rule numbers.

- Use the plain word: "use", "help", "many", "if" [31]. Drop "additionally", "crucial", "delve", "enhance", "leverage", "pivotal", "robust", "seamless" [7].
- Say "is" or "has", not "serves as" or "boasts" [8].
- Give a number or a name instead of an adjective: "within 5 seconds", not "fast" [27, 30]. If a sentence could appear unchanged in another project's docs, cut it [27].
- Don't end a sentence with an "-ing" phrase such as "ensuring..." or "highlighting..." [3].
- State the point. Don't write "not just X, but Y" [9].
- List as many items as there are. Don't force them into threes [10].
- Pick one name for a thing and repeat it. Don't cycle synonyms [11].
- Use the concrete word, not a metaphor noun: "base", not "substrate", and "add", not "wedge in" [26].
- Name the actor: "the API rejects the request", not "the request is rejected" [29].
- Keep one idea per sentence, and split a sentence the reader would have to read twice [28].
- Write whole sentences, with articles and verbs. No arrows or symbol-speak in prose [33].
- No em dashes [13]. Use a colon only before a list or an example [14].
- Write headings in sentence case [17].
- Bold only what a reader scans for. A bold lead-in ends with a period and adds new detail [15, 16].
- No filler such as "in order to" or "it is important to note" [23], no stacked hedges [24], no closing summary [25].
- No chat phrases such as "Certainly!" or "I hope this helps" [20], and no praise of the user such as "Great question!" [22].
- Use straight quotes [19] and no emoji [18].

These rules don't apply to IDs, markers, code, quoted user text, or headings that a template fixes.
